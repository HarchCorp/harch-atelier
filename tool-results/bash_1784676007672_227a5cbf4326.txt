- **Architectural decisions**: (1) All entities sections follow the trader + admin + legal + comms pattern exactly: `SectionHeader` (with `accent="amber"` for the market role tint, `statusChips`, `kpis`) + `ChartCard` body + reusable `DeferredChart` for chart mounts. (2) Market accent is amber-700 across all 5 sections for role identity (vs legal=violet, admin=rotating, trader=emerald, pr=rose). (3) All tables use shadcn `<Table>` primitives with `max-h-[N] overflow-y-auto harch-scroll` for long lists. (4) All charts use recharts via `DeferredChart` to avoid ResponsiveContainer flash. (5) The entities dataset REUSES `moroccanEquities` + `BvcSector` from `./market-data` and EXTENDS them with private Moroccan corporates + peers + counterparties (no duplication). (6) The dataset is fully self-contained — no `any`, deterministic via mulberry32 seeded (seed 20251118) so first paint is stable. (7) The directory table's `SortHeader` is declared at module scope (not inside the component) to satisfy ESLint's `react-hooks/static-components` rule — passed `active`/`dir`/`onClick` as explicit props. (8) The peer scatter uses recharts `ScatterChart` with `ZAxis` for bubble size — bubbles colored per-entity by sector color, with an orange `ReferenceLine` at y=55 marking the high-risk threshold. (9) The peer ranking bars overlay a thin vertical risk marker (positioned left-right by risk score, colored by severity) on top of the revenue-share bar — gives a compact "is this peer's risk proportional to its revenue?" visual. (10) The watchlist card sparkline uses recharts `AreaChart` with a per-card gradient id (`wlsGrad-${signal.id}`) — small enough that no axes are needed. (11) The profile selector uses shadcn `Tabs` with horizontal-scrollable `TabsList` (`flex-wrap` on small screens) — each tab shows the entity ticker in a colored mini-avatar. (12) HarchCorp self entity is tinted amber-50/40 across all sections (directory row, moroccan list entry, profile tab trigger, watchlist cards) — visually distinguishes the monitored self from peers/counterparties/listed.
- **Issues/risks**: (1) The directory table has 11 columns which gets tight on mobile (390px); the table uses `max-h-[560px] overflow-y-auto harch-scroll` for vertical scroll but horizontal overflow is acceptable for a dense directory matrix — mobile users will see the first ~6 columns cleanly and can scroll horizontally for the rest. (2) The peer benchmark table's ROE calculation is a simplified heuristic (`netIncome / (assets - mktCap)`) — for a real production deployment this would come from a financial-data vendor (Bloomberg / FactSet) and would include proper shareholder-equity adjustments. (3) The watchlist sparkline is a 20-point series with no axes — for hover precision a real sparkline would show a tooltip; here it's purely decorative pulse-visual. (4) The 41-entity directory is intentionally compact (one page); for a real production deployment with hundreds of entities, server-side pagination + virtual scrolling would be needed (the current `max-h-[560px] overflow-y-auto` works for 41 but not 4000). (5) The ownership pie uses a fixed 5-color palette (amber/sky/emerald/violet/slate) — entities with > 5 shareholders would cycle colors; current data caps at 4 shareholders per entity so this isn't hit. (6) The peer scatter's `ZAxis` range `[60, 1200]` is calibrated for the Banking peer group (largest mkt cap ~105B MAD ATW); for the Insurance peer group (smaller caps ~3-8B MAD) the bubbles render smaller — acceptable, but a per-group auto-range would be a future enhancement.
